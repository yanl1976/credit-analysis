# 合作方资信分析系统 · 设计方案（V1）

> 定位：以**客户（销售/应收方向）**为主体，聚焦**回款能力、信用与诉讼风险**；
> 数据范围：**国内企业为主**；数据来源：**纯外部**（天眼查 / 企查查等商业 API），内部 ERP 数据后续再补。

---

## 1. 业务目标与边界

### 1.1 要解决的核心问题
销售人员/风控在给客户赊销、定账期、定授信额度前，缺乏一个**统一的、可解释的客户风险视图**。本系统把分散在各公开渠道的客户信用信息收敛成：
- 一份**客户资信报告**（人工尽调时看）；
- 一个**信用等级 + 风险评分**（审批流/授信时用）；
- 一条**预警线**（客户出现新增被执行、失信、经营异常时主动提醒）。

### 1.2 本期不做（避免范围蔓延）
- 不接内部金蝶 ERP（应付/应收账期等）— 二期再补，但 schema 预留 `internal_*` 字段。
- 不做国际化（D&B/制裁名单等）— 二期再补。
- 不接实时交易决策，只输出"参考评级 + 报告"，最终授信由人决定。
- 不碰需要央行征信资质的个人征信业务。

## 2. 总体架构（分层）

```
┌─────────────────────────────────────────────┐
│  应用层  Web 前端 (Vue3+ElementPlus+ECharts) │  组织权限 / 客户报告 / 风险看板 / 批量导入 / 预警中心
├─────────────────────────────────────────────┤
│  服务层  API + 评分引擎 + 预警引擎           │  统一接口 / 评分卡计算 / 等级与预警
├─────────────────────────────────────────────┤
│  数据模型层  主体归一 + 维度宽表 + 评分结果  │  partner 主表 + 各维度子表 + rating
├─────────────────────────────────────────────┤
│  实体解析层  企业主体归一                     │  统一社会信用代码为主键，名称模糊兜底
├─────────────────────────────────────────────┤
│  采集适配层  渠道 Connector（可插拔）         │  天眼查（主力）/ 企查查（备用）
└─────────────────────────────────────────────┘
        ↑ 调度层（定时重拉 + 变更检测，二期）
```

**关键设计原则**
- **渠道可插拔**：每个数据源实现一个 `Connector` 接口（`search / fetchDetail / normalize`），新增渠道不改核心逻辑。
- **以统一社会信用代码（`creditCode`）为主键**：这是国内企业唯一稳定标识，所有维度都挂到它下面。名称只做"检索入口"和"兜底匹配"。
- **原始数据落盘（`partner_raw`）**：每次采集的原始 JSON 都存一份，便于追溯、重算、审计，也避免频繁打第三方 API。

## 3. 数据维度与渠道（针对客户/应收）

| 维度 | 关键信号 | 推荐渠道 | 接入方式 | 说明 |
|---|---|---|---|---|
| 工商基础 | 存续状态、注册资本、成立年限、股东/实控人、变更 | 企查查 / 天眼查 API | 付费 API | 主体信息基座，必接 |
| 司法风险 | 裁判文书（原/被告）、被执行人、失信、限高、破产 | 天眼查：企业三要素验证（主体核实）+ 后续司法类接口 | 付费 API | **回款风险最核心信号**；需购买对应接口 |
| 信用/经营 | 经营异常、严重违法失信、行政处罚、重大税收违法、欠税、税务非正常户 | 天眼查：经营异常/严重违法/行政处罚/税收违法/欠税公告/税务非正常户 | 付费 API（已开通） | 直接反映经营合规 |
| 财务线索 | 上市财报（营收/净利/同比）、招投标、招聘规模、参保人数 | **上市公司或其子公司**：东方财富 / 巨潮资讯 / 交易所公告（公开财报）；非上市：企查查/天眼查替代数据 | 公开网站 + API | 上市口径优先取真实财报，非上市才用替代数据 |
| 舆情 | 负面新闻、处罚曝光 | 舆情监控（可选，二期） | API/爬虫 | 辅助，权重低 |

> 渠道选型建议：**统一走商业 API（天眼查优先，企查查备用）**，省去多源拼接与口径不一致。
> **公开渠道已剔除（2026-10-19 决策）**：信用中国、执行信息公开网均已启用验证码 + WAF，自动采集不可行；绕过验证码既不稳定也不合规，故不再注册这两个 Connector，其内容由天眼查对应接口覆盖。裁判文书网同理，二期若需司法明细，以购买天眼查司法类接口为准。
> **配置驱动（暂无账号也能启动）**：每个渠道的启用开关与 API Key 全部外置到 `config/channels.*`，Connector 在初始化时检测配置是否齐全——未配置或开关关闭的渠道自动跳过并在日志/前端提示"未配置"，核心骨架（组织/客户/评分/报告）不依赖任何外部账号即可跑通；账号到位后填入配置即生效，无需改代码。

### 3.1 天眼AI（官方 MCP 服务）· 免费通道

天眼查面向 AI 助手开放了 MCP 服务，与「开放平台按次计费 API」是**两条独立通道**，可并存：

| 项 | 值 |
|---|---|
| 端点 | `https://mcp.tianyancha.com/v1`（注意不能带尾斜杠，否则 404） |
| 协议 | Streamable HTTP + JSON-RPC 2.0（响应可能是 `application/json` 或 `text/event-stream`） |
| 鉴权 | `Authorization: Bearer <MCP Key>`（`mcpk`/`tyc` 开头） |
| 会话 | `initialize` 响应头返回 `Mcp-Session-Id`，后续请求回传，并发送 `notifications/initialized` |
| 配置 | `.env` 的 `TIANYANCHA_MCP_TOKEN` / `TIANYANCHA_MCP_URL` / `TIANYANCHA_MCP_TIMEOUT_MS` |

> **鉴权口径（实测）**：服务端明确拒绝开放平台裸 token —— `raw OpenAPI tokens are not accepted; use OAuth or an MCP API key`。
> 即 `TIAN_YAN_CHA_API_KEY` 不能用于 MCP，必须用控制台复制出来的 MCP Key。

**免费会员可用工具（企业维度 5 个）**：`search_companies`（主体锚定）、`get_company_registration_info`（登记信息）、
`get_company_profile`（简介）、`get_risk_overview`（风险总览·聚合计数）、`get_ipr_score`（创新力评分）、
`verify_company_accuracy`（二/三要素核验）。
**需 VIP/SVIP**：裁判文书、立案、开庭、被执行人、失信、限高、经营异常、行政处罚、股东、对外投资、招投标、财务、专利商标等 66 个。
调用前必须先 `get_company_capabilities(company_id)` 拿真实 `tool_name`，不能凭经验猜工具名。

**落库口径**：MCP 结果写入 `partner_raw`（`channel='tianyancha_mcp'`，`biz_key` 为工具短名），
**不伪造逐条案件**——`partner_judicial` / `partner_credit` 仍只接受真实明细（手工录入或 VIP 明细接口）。
报告页首个页签「企业画像」（默认展示）展示登记信息、简介、风险总览分组计数与创新力评分。

## 4. 数据 Schema 设计

> 数据库使用 **MySQL 8**（`mysql2` 驱动，纯 JS 无需编译），经 `src/db.js` 统一封装 `db.all/get/run/exec`；生产先 MySQL 8，信创验收前切换达梦/人大金仓（MySQL 兼容协议），业务代码零改动。表名避开 MySQL 保留字（`user`/`role` → `sys_user`/`sys_role`），字符集统一 utf8mb4、引擎 InnoDB。

### 4.0 组织与权限（集团 + 多级子公司）
- `org`（组织树）：`id`、`parent_id`(自引，集团根 `parent_id=0`)、`org_name`、`org_type`('GROUP'集团 / 'SUB'子公司)、`level`、`path`(祖先后代路径，如 `/1/3/7`，便于子树查询与递归授权)。
- `sys_user`（用户，避开 MySQL 保留字 `user`）：`id`、`org_id`(关联 org)、`username`、`password_hash`、`status`。
- `sys_role`（角色，避开保留字 `role`）：`id`、`org_id`、`role_key`('ADMIN' / 'MANAGER' / 'VIEWER')、`role_name`。
- `sys_user_role`：`user_id`、`role_id`。
- `sys_permission`（功能权限）：与角色关联，控制菜单/操作（系统管理、渠道配置、客户管理、报告查看、预警查看）。
- **数据作用域（核心隔离机制）**：`partner.owner_org_id` 标记客户归属组织；查询时按当前用户组织作用域过滤——集团用户可见全部，子公司用户仅可见本组织及下属（`path` LIKE 匹配）。这就实现"集团统管全局、子公司有限权限"。
- **两级权限语义**：
  - *管理权限*：能否配置渠道、管理用户/组织、查看全局 —— 仅集团管理员与子公司管理员持有。
  - *使用权限*：能否查看/录入/导出本组织客户 —— 管理员与查看员均持有，但范围受 `owner_org_id` 限制。
  - 预置角色：集团管理员（全量+管理）、子公司管理员（本组织管理+使用）、子公司查看员（本组织只读）。

### 4.1 主体主表 `partner`（含归属组织，支持数据隔离）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| owner_org_id | BIGINT | 客户归属组织（数据隔离用，关联 `org.id`） |
| credit_code | TEXT(18) UNIQUE | 统一社会信用代码（主体唯一键） |
| name | TEXT | 企业名称 |
| alias_names | JSON | 曾用名/别名数组 |
| legal_person | TEXT | 法定代表人 |
| reg_status | TEXT | 存续/吊销/注销/迁出 |
| province | TEXT | 省份 |
| industry | TEXT | 行业门类 |
| data_source | VARCHAR(16) | 数据来源：`manual` 手工录入（默认）/ `demo` 演示数据 / `channel` 渠道采集 |
| created_at / updated_at | DATETIME | 时间戳（应用层填充） |

> **数据来源必须真实标注**：演示数据一律 `data_source='demo'`，前端以橙色「演示数据」标签展示，
> 看板单独统计「其中演示 X 家」，不得与手工/渠道数据混同。

### 4.2 各维度子表（均按 `partner_id` 关联，一对多）
- `partner_judicial`（司法）：`case_type`(裁判/执行/失信/限高/破产)、`party_role`(原告/被告，避 MySQL 保留字)、`case_no`、`court`、`amount`(标的/执行金额)、`status`、`date`、`detail_json`。
- `partner_credit`（信用/合规）：`item_type`(经营异常/行政处罚/严重违法失信/税收违法)、`authority`、`reason`、`penalty`、`date`、`detail_json`。
- `partner_finance`（财务线索）：`src`(来源站点：东方财富/巨潮资讯/企查查)、`stock_code`(股票代码)、`report_period`(报告期)、`listed_status`(本公司上市/母公司上市/未上市)、`rev_yoy`、`profit`、`scale_tag`、`employee_cnt`、`bid_cnt`、`detail_json`。
- `partner_raw`（原始缓存）：`channel`、`biz_key`、`payload_json`、`fetched_at`。

### 4.3 评分结果 `partner_rating`
| 字段 | 类型 | 说明 |
|---|---|---|
| partner_id | BIGINT PK | 关联 partner |
| score | INTEGER | 0~100，越高越安全 |
| grade | TEXT(8) | AAA/AA/A/B/C/D |
| risk_level | TEXT(8) | 低/中/高/极高 |
| veto | INTEGER(0/1) | 一票否决（失信/破产/吊销） |
| reasons | JSON | 扣分/否决明细（可解释） |
| calc_version | TEXT(16) | 模型版本，便于回溯 |
| calculated_at | DATETIME | 计算时间 |

### 4.4 采集任务与日志（二期监控用）
- `fetch_task`：`partner_id`、`channel`、`status`、`cost_ms`、`err_msg`、`created_at`。
- `risk_event`（预警）：`partner_id`、`event_type`、`old_grade`、`new_grade`、`detail`、`created_at`。

### 4.5 系统设置 `sys_setting`（功能开关，白名单驱动）
- 字段：`setting_key`（PK）、`setting_value`、`description`、`updated_at`。
- **白名单登记制**：新增开关只在 `src/services/setting-service.js` 的 `SETTING_DEFS` 登记（类型/默认值/范围/说明），
  前端「系统设置 → 功能开关」按类型自动渲染，未知 key 的写入被忽略（防越权写入）。
- 已生效开关（全部有真实消费方，不做"假开关"）：
  | key | 类型 | 默认 | 消费方 |
  |---|---|---|---|
  | `system.name` | string | 合作方资信分析系统 | 登录页 / 侧边栏标题（`/api/settings/public`） |
  | `system.owner` | string | 空 | 系统信息展示 |
  | `scoring.autoRecalcOnCollect` | boolean | true | 采集完成后自动重算评分（`collectPartner`） |
  | `warning.recordGradeChange` | boolean | true | 等级变化是否写 `risk_event`（`ratePartner`） |
  | `collect.recordRaw` | boolean | true | 是否保存渠道原始报文到 `partner_raw` |
  | `ui.pageSize` | number(10~100) | 20 | 客户 / 预警列表默认分页 |
- 接口：`GET /api/settings`（分组+项）、`PUT /api/settings`（批量，`{values:{...}}`）、
  `GET /api/settings/channels`（渠道状态，不含 Key）、`GET /api/settings/public`（登录前可读：名称/分页/版本）。

### 4.6 手工录入（渠道不可用时的真实数据入口）
- 场景：无企查查/天眼查 Key 时，由风控人员按尽调材料录入司法、合规、财务三类记录。
- 接口（均需 `customer:manage` + 数据作用域）：
  `POST/PUT/DELETE /api/partners/:id/{judicial|credit|finance}[/:itemId]`；
  列表沿用 `GET /api/partners/:id/{judicial|credit|finance}`。
- 字段映射：请求体为 camelCase（`caseType/partyRole/caseNo/amount/...`），落库为 snake_case。
- 录入/修改/删除成功后按开关 `scoring.autoRecalcOnManual`（默认开）自动重算评分并写历史，
  响应返回 `{ item, scored }`，前端直接提示新分数与新等级。
- 评分消费口径与采集数据完全一致（同一 `partner_judicial/credit/finance` 表），不存在两套逻辑。

### 4.7 AI 辅助（档案填充 + 信息检索）
- 模型：OpenAI 兼容 `chat/completions`（默认 MiniMax，`.env` 的 `USE_LLM`/`MINIMAX_API_KEY`/`MINIMAX_MODEL`）。
- **联网检索是可选项**：配置 `TAVILY_API_KEY` / `SERPER_API_KEY` / `BING_SEARCH_KEY` 任一即启用，
  AI 分析前先检索网页、把摘要作为「证据」注入提示词并要求引用；**未配置时模型无联网能力**，
  只能凭已有知识推断，响应中 `meta.search.configured=false` 明确标注。
- 接口：
  - `GET /api/ai/status`：模型与搜索通道状态（前端据此显示/隐藏 AI 按钮）；
  - `POST /api/ai/partner-profile`（`customer:manage`）：输入企业名称 → 档案草稿（**不落库**），
    返回 `profile / confidence / notes / evidence / meta.requiresReview`；
  - `POST /api/ai/collect/:id`（`customer:manage` + 数据作用域）：按客户名称检索司法/信用/财务信息，
    写入对应维度表（`data_source='ai'`），原始返回落 `partner_raw`（`channel='ai'`），随后重算评分。
- **防幻觉约束**：提示词要求「无证据不得编造、不确定填 null」；信用代码做 18 位正则校验后才回填；
  重复条目按案号/类型+日期/来源+标签去重（响应 `added.skipped`）。
- **数据可信度标注**：AI 生成的客户与维度记录一律 `data_source='ai'`，前端显示红色「AI 推断」标签，
  保存前必须人工核验。实测同一企业两次调用，模型给出的省份可能不同 → 不可作为权威数据直接使用。

### 4.8 系统管理接口鉴权（组织 / 人员 / 角色 / 设置）
- 组织：`GET /orgs`、`GET /orgs/tree` 登录即可读（客户归属组织下拉需要）；增删改需 `system:manage` + 数据作用域。
- 人员、角色、设置、渠道状态：全部需 `system:manage`；列表按当前用户数据作用域过滤（集团全量、子公司本组织子树），
  跨作用域写操作返回 403。
- 组织删除保护：存在子组织 / 用户 / 角色时拒绝删除。

> **预留内部 ERP 字段**：`partner` 表预留 `internal_customer_no`、`internal_ar_amount`、`internal_ar_aging` 等列（默认 NULL），二期直连金蝶时填充，不影响本期模型。

## 5. 评分模型（规则评分卡，可解释优先）

### 5.1 设计思路
客户资信的核心是**"能不能回款、会不会坏账"**。因此**司法与经营状态权重最高**，财务线索与舆情作辅助。先用**专家加权评分卡**（业务看得懂、可直接调权重），ML 模型留到数据积累后迭代。

### 5.2 维度权重（V1 建议，可配置）
| 维度 | 权重 | 主要子指标 | 扣分逻辑 |
|---|---|---|---|
| 司法风险 | 35% | 失信被执行、限高、破产、作为被告的未结诉讼金额 | 失信/破产直接否决；被执行按金额阶梯扣分；被告诉讼多扣分 |
| 经营状态/合规 | 25% | 存续状态、经营异常、行政处罚、严重违法失信 | 吊销/注销/破产否决；经营异常/处罚按次数扣分 |
| 工商健康度 | 20% | 成立年限、注册资本、股东背景、变更频率 | 成立<1年、注册资本过低、频繁变更扣分 |
| 财务/经营线索 | 15% | 规模标签、参保/招聘、招投标活跃度 | 规模越小风险越高（替代数据，权重克制） |
| 舆情 | 5% | 负面新闻条数 | 少量扣分，仅辅助 |

### 5.3 一票否决（Veto，直接定级 D/极高）
满足任一即 `veto=1`、风险等级"极高"、评分封顶：
- 被列入**失信被执行人**或**破产**；
- 工商状态为**吊销/注销**；
- 存在未结**限制高消费**且标的较大。

> **落地口径（V1.0，`config/scoring.js`）**：否决客户的 `score` 封顶为 `vetoScoreCap = 25`（`<25 或 veto → D`），
> 封顶差额以 `category='否决'` 记入 `reasons`（如「一票否决：评分封顶 25 分 -70」），避免出现「95 分 / D 级」的矛盾展示。
>
> **扣分口径（防重复）**：被执行案件按「单条 -8 + 金额阶梯」计分；`失信/破产/限高` 只作否决不再扣分；
> 「作为被告的未结**诉讼**」仅统计**裁判类**案件，`执行/失信/破产/限高` 案由不重复计入被告未结条数。

#### 5.3.1 财务红线（V1.2 落地，`config/scoring.js` 的 `financeVeto`）

**问题**：司法/合规渠道无 Key 时，两维度无数据即不扣分，一家实质失去偿债能力的上市公司会被算成满分 AAA。

**口径**：当且仅当同时满足 `资产负债率 ≥ 80%` 且 `最近连续亏损年数 ≥ 2`，视为偿债能力已实质恶化，
评分封顶 `39` 分、等级 `C`、风险等级 `高`（不升级为 D，D 仍由司法/工商一票否决独占），
并在 `reasons` 记一条 `财务红线` 说明。该规则可通过 `financeVeto.enabled=false` 关闭。

**财报科目扣分（`deductions.finance.statement`，合计下限 -30）**：仅在客户存在
`partner_finance.detail_json.fiscal` 结构化财报时生效，对所有无财报数据的客户零影响：

| 指标 | 口径 | 扣分 |
|---|---|---|
| 资产负债率 | 负债合计 / 资产合计 | ≥90% -12、≥80% -9、≥70% -6、≥60% -3 |
| 流动比率 | 流动资产 / 流动负债 | <1 -5、<1.2 -3 |
| 利息保障倍数 | (利润总额 + 利息费用) / 利息费用 | ≤0 -6、<1 -4、<3 -2 |
| 连续亏损年数 | 年报归母净利连续为负的年数 | 每年 -2，下限 -10 |
| 经营现金流 | 最近一期经营活动现金流量净额 | 为负 -4 |
| 有息负债/净资产 | (短借+一年内到期+长借+租赁负债) / 所有者权益 | ≥2 -5、≥1 -3；净资产为负按 -5 |

> 财报数据缺失的维度不扣分、也不给"正向加分"，并在 `reasons` 记 `数据` 维度的一条「完整性受限」提示。

#### 5.3.2 外部风险概览（V1.3，天眼AI 聚合口径）

免费权益只能拿到「自身风险」的**聚合计数**（无案号/角色/金额），因此不逐条扣分，按档代理：

| 指标 | 口径 | 扣分 |
|---|---|---|
| 自身·立案信息 | 已被法院受理的案件数（角色未知） | ≥20 -12、≥10 -9、≥5 -6、≥1 -3 |

**只在逐条明细不足时启用**：当 `天眼自身立案数 > partner_judicial 记录数` 才补扣，明细齐全则不重复计算。
同一主体的 `周边风险`（关联方担保/被执行等）与 `历史风险` **不参与本企业评分**，仅在报告页展示。

> **V1.3 同时修正两处判定错误**：
> ① 「执行案件」只有 `party_role` 含 **被执行人** 才扣分，作为 **申请执行人**（原告/债权人）属追偿行为，不扣分；
> ② 被执行金额阶梯扣分不再在 `reasons` 中重复展示（原实现 tier 与合并后 delta 各推一条，导致明细合计大于实际扣分）。

### 5.4 等级映射
```
score >= 85  → AAA（低风险）
70~84        → AA
55~69        → A
40~54        → B（中风险，缩短账期/降低授信）
25~39        → C（高风险，现款现货/拒赊）
<25 或 veto  → D（极高，禁合作）
```

### 5.5 可解释输出（关键）
每次评分都生成 `reasons`（例如）：
```
[-30] 失信被执行人 1 条（标的 120万，未结）
[-15] 近1年作为被告诉讼 4 起（合计 380万）
[-10] 经营异常 2 次（地址失联）
[+5]  成立 8 年、注册资本 5000万（正向）
=> 总分 45 → 等级 B
```
前端报告直接展示这张明细表，让销售/风控知道"为什么是这个分"。

### 5.6 模型版本化
评分逻辑用 `calc_version` 标记（如 `v1.0`），每次调权重升版本，历史评分可回溯对比，避免"分数变了说不清"。

## 6. 技术栈建议（复用现有经验）

- **后端**：Node ESM + 统一数据层 `src/db.js`（**MySQL 8 / `mysql2` 驱动**，纯 JS 无需编译）；Connector 用可插拔类 + 配置化渠道开关（API Key/渠道开关外置 `config/`，暂无账号也能启动，配置为空时跳过该渠道并提示）。
- **信创适配**：先 MySQL 8，信创验收前切达梦/人大金仓（MySQL 兼容协议）；业务代码只走 `db.all/get/run/exec` 统一接口，切换仅改连接参数，零改动；严格避免数据库特定函数与时间/类型方言差异。
- **前端**：Vue3 + Vite + Element Plus + Pinia + ECharts（与 safety 项目一致），页面：客户列表/检索、客户资信报告、风险看板、预警中心、批量导入。
- **调度**：`node-schedule` 做定时重拉 + 变更检测（二期）。
- **配置**：渠道 API Key、权重表、否决规则外置到 `config/`，不写死在代码里。
- **合规**：所有第三方调用走授权 API；公开渠道抓取遵守 robots 与频率限制；原始数据按 PIPL 做脱敏与访问留痕。
